MongoDB

Explain the aggregation pipeline and its stages.

🎤 Interview Answer

The aggregation pipeline is MongoDB's framework for transforming and analyzing documents in stages, where each stage takes the output of the previous stage as its input, similar to a Unix pipe. Common stages are $match to filter documents, $group to aggregate values like sums or counts, $sort, $project to reshape documents, $limit, and $lookup to join data from another collection. I use aggregation whenever I need something more than a simple find — like computing revenue per category, joining orders with users, or building a dashboard summary. The order of stages matters a lot for performance: I always try to put $match and $sort as early as possible so MongoDB can use indexes and reduce the working set before doing expensive operations like $group or $lookup.

🧠 Understand It

Aggregation exists because a plain find() can only filter and shape a single collection — it can't easily compute derived values or combine data. The pipeline solves this by chaining small, composable operations. Each stage receives a stream of documents and passes a transformed stream to the next stage, so you build complex analytics by combining simple steps rather than writing one giant query. You reach for aggregation when you need grouping, joins, computed fields, or multi-step reshaping; you avoid it for simple lookups where find() with a projection is faster and easier to read.

🔄 How It Works 
Documents
   ↓
$match (filter early, use indexes)
   ↓
$group / $lookup (heavy lifting)
   ↓
$sort / $project (shape output)
   ↓
$limit
   ↓
Result cursor
💡 Practical Example

On an e-commerce site, you might aggregate the orders collection to find total revenue per product category for the last 30 days, joining in product names via $lookup, for a seller analytics dashboard.

💻 Code Example 
const revenueByCategory = await Order.aggregate([
  { $match: { createdAt: { $gte: thirtyDaysAgo } } },
  { $lookup: { from: "products", localField: "productId", foreignField: "_id", as: "product" } },
  { $unwind: "$product" },
  { $group: { _id: "$product.category", total: { $sum: "$amount" } } },
  { $sort: { total: -1 } }
]);

$match filters orders down to the last 30 days first so later stages work on far fewer documents. $lookup joins in product data, $unwind flattens the joined array, $group sums revenue per category, and $sort ranks the results — all in one round trip to the database.

❓ Follow-Up Questions

Q: Which stages can use an index, and why does stage order matter?

Answer: Only $match, $sort, and $geoNear (when they're the first stage) can use an index; putting $match first lets MongoDB use IXSCAN instead of scanning every document.

Q: What's the difference between $match early vs late in a pipeline?

Answer: Early $match reduces the document count before expensive stages like $group or $lookup run, which is far cheaper than filtering after those stages have already processed everything.

Q: When would you use $group vs $bucket?

Answer: $group aggregates by an exact key you specify; $bucket groups numeric or date values into ranges you define, which is better for histograms.

Q: What happens when a pipeline exceeds the 100MB memory limit, and how do you design around it?

Answer: MongoDB throws an error unless you set allowDiskUse: true, which spills intermediate stages to disk; you can also redesign the pipeline to filter earlier so less data ever reaches memory-heavy stages.

⚠️ Common Interview Traps
  • ❌ Aggregation is just a fancy way to write a query.
    ✅ Aggregation is a data transformation pipeline — it's for computing and reshaping, not just filtering; use find() for simple lookups.
  • ❌ Stage order doesn't matter since MongoDB optimizes it for you.
    ✅ MongoDB does some pipeline optimization, but you should still manually put $match/$sort early — relying entirely on the optimizer is risky.
📌 What to Remember
  • Pipeline = ordered array of stages, each transforming the previous output.
  • Put $match and $sort as early as possible to use indexes.
  • $group, $project, $lookup, $unwind, $facet are the workhorses.
  • allowDiskUse handles pipelines that exceed the 100MB memory limit.
  • Use explain() to see which stages actually hit an index.

How does indexing work in MongoDB, and what are compound indexes?

🎤 Interview Answer

An index in MongoDB is a separate data structure — a B-tree — that stores a sorted copy of one or more fields along with a pointer back to the full document, so queries on that field don't have to scan every document in the collection. Without an index, MongoDB does a collection scan (COLLSCAN), checking every document one by one. A compound index is an index on multiple fields together, like { userId: 1, createdAt: -1 }, and it's especially powerful because it can satisfy queries that filter on the first field and sort or range-query on the second, all from a single index. The order of fields in a compound index matters enormously — MongoDB follows what's called the ESR rule: Equality fields first, then Sort fields, then Range fields, because that ordering lets the index narrow down results as early as possible.

🧠 Understand It

Indexes exist because scanning millions of documents for every query would make an application unusably slow. By keeping a sorted structure on disk, MongoDB can binary-search to the matching range instead of scanning linearly. You add indexes on fields you frequently filter, sort, or join on. The tradeoff is that every index adds overhead on writes (each insert/update has to update every relevant index) and uses additional storage, so you shouldn't index every field — only the ones that actually appear in your query patterns.

🔄 How It Works 
Query arrives
   ↓
Query planner checks available indexes
   ↓
Picks index matching filter/sort (IXSCAN) or falls back to COLLSCAN
   ↓
B-tree lookup narrows to matching range
   ↓
Documents fetched by pointer
💡 Practical Example

A social app querying "posts by this user, newest first" benefits hugely from a compound index on { userId: 1, createdAt: -1 } — a single index serves both the filter and the sort.

💻 Code Example 
// Create a compound index
db.posts.createIndex({ userId: 1, createdAt: -1 });

// This query uses the index fully
db.posts.find({ userId: id }).sort({ createdAt: -1 });

The equality field (userId) comes first so MongoDB can jump straight to that user's documents, and createdAt is already stored in descending order within that range, so no separate in-memory sort is needed.

❓ Follow-Up Questions

Q: Explain the ESR rule (Equality, Sort, Range) for compound index field order.

Answer: Put equality-filtered fields first, then fields you sort on, then range-filtered fields last — this order lets the index eliminate the most documents as early as possible.

Q: Given an index on {a:1, b:1, c:1}, which query shapes can use it?

Answer: Any prefix of the index — queries on just a, on a+b, or a+b+c — but not queries that skip a or only filter on b or c alone.

Q: What's the difference between a sparse and a partial index?

Answer: A sparse index skips documents missing the indexed field entirely; a partial index is more flexible — it only indexes documents matching a filter expression you define.

Q: What's the write-path cost of each additional index, and how do you decide to drop one?

Answer: Every write has to update every index on that document, so many unused indexes slow down writes; I check $indexStats to find indexes with near-zero usage and drop those.

⚠️ Common Interview Traps
  • ❌ More indexes always make queries faster.
    ✅ Indexes speed up reads but slow down writes and use storage — only index fields your real query patterns actually use.
  • ❌ Field order in a compound index doesn't matter as long as all fields are included.
    ✅ Order is critical — an index on {a,b} cannot efficiently serve a query filtering only on b.
📌 What to Remember
  • Index = B-tree structure for fast lookup instead of full scans.
  • Compound index field order follows Equality → Sort → Range.
  • A compound index can serve any left-to-right prefix of its fields.
  • Every index adds write overhead — don't over-index.
  • Use explain() and $indexStats to validate index usage.

What's the difference between find(), findOne(), and aggregate()?

🎤 Interview Answer

find() returns a cursor to all documents matching a filter, which you can then iterate, sort, limit, or project — it's the general-purpose way to read data. findOne() is a convenience wrapper that returns just the first matching document as a plain object instead of a cursor, which is handy when you expect at most one result, like looking up a user by email. aggregate() is a completely different, more powerful tool — it runs a multi-stage pipeline that can filter, group, join, and reshape data, doing things find() simply can't, like computing sums across documents or joining two collections. In practice, I use findOne() for single-record lookups, find() for lists with simple filtering, and reach for aggregate() only when I need computation or joins that plain queries can't express.

🧠 Understand It

These three exist at different levels of complexity for a reason: most reads are simple lookups, so find()/findOne() keep those fast and easy to write. But some reads genuinely need transformation — like "average order value per month" — and that's not something you can express as a filter, so aggregate() exists as a separate, more expressive pipeline engine. Reaching for aggregate() when find() would do adds unnecessary complexity and can even be slower for simple cases.

💡 Practical Example

Fetching a single user profile by ID uses findOne(); listing a user's last 20 orders uses find().sort().limit(); calculating that user's total lifetime spend uses aggregate() with a $group stage.

💻 Code Example 
const user = await User.findOne({ email });
const orders = await Order.find({ userId }).sort({ createdAt: -1 }).limit(20);
const [{ totalSpend }] = await Order.aggregate([
  { $match: { userId } },
  { $group: { _id: null, totalSpend: { $sum: "$amount" } } }
]);

findOne stops as soon as it finds a match, find() returns a full cursor you can chain methods on, and aggregate runs a pipeline that computes a derived value no simple query could produce.

❓ Follow-Up Questions

Q: When would you use aggregate() for something find() could do?

Answer: Almost never intentionally — but if you already have a complex $match/$project pipeline for other reasons, adding a $limit:1 might replace a separate findOne() call.

Q: Does findOne() stop scanning after the first match if there's no index?

Answer: Yes — findOne() stops at the first matching document it encounters, but without an index that could still mean scanning a significant portion of the collection.

Q: How does projection differ between find() and $project?

Answer: find()'s projection argument only includes/excludes fields; $project in aggregation can also compute new fields, rename them, and reshape nested structures.

Q: When do you push logic into the DB vs into the app layer? What drives that call?

Answer: I push into the DB when it avoids transferring large amounts of data over the network or avoids N+1 queries; I keep it in the app layer when the logic needs external services or is more maintainable in code.

⚠️ Common Interview Traps
  • ❌ aggregate() is just a slower version of find().
    ✅ They serve different purposes — aggregate() can do things find() structurally cannot, like grouping and joining.
📌 What to Remember
  • find() → cursor of matches; findOne() → single document or null.
  • aggregate() → multi-stage pipeline for transformation, grouping, joins.
  • Don't reach for aggregate() when a simple filter would do.
  • findOne() short-circuits at the first match.
  • $project in aggregation can compute new fields; find()'s projection can't.

How do you optimize MongoDB queries for performance?

🎤 Interview Answer

Query optimization in MongoDB starts with explain(), which shows exactly how the query planner executed a query — whether it used an index (IXSCAN) or scanned the whole collection (COLLSCAN), how many documents it examined versus returned, and how long it took. My general approach is: identify slow queries with the profiler or logs, run explain() on them, add or fix indexes so the query hits IXSCAN instead of COLLSCAN, and aim for a covered query where possible — one where the index alone contains all the fields the query needs, so MongoDB never has to touch the actual documents. Beyond indexing, I also look at whether I'm over-fetching fields with no projection, whether pagination uses skip() at high offsets (which degrades badly), and whether a query could be restructured to do less work, like moving a filter earlier in an aggregation pipeline.

🧠 Understand It

Performance problems in MongoDB almost always come down to the database doing more work than necessary — scanning too many documents, transferring too much data, or sorting in memory instead of using an index. explain() exists precisely to make that work visible instead of guessing. You optimize proactively for known access patterns (index the fields you filter/sort on) and reactively for measured slow queries (use the profiler to find what's actually hurting in production, which is often not what you'd guess).

🔄 How It Works 
Slow query reported
   ↓
db.collection.find(...).explain("executionStats")
   ↓
Check: totalDocsExamined vs nReturned, stage (IXSCAN/COLLSCAN)
   ↓
Add/adjust index → re-run explain
   ↓
Confirm covered query or acceptable examine ratio
💡 Practical Example

An admin dashboard listing "orders over $500 in the last week, sorted by date" was slow at scale; adding a compound index on { amount: 1, createdAt: -1 } turned a full collection scan into an index-only lookup.

💻 Code Example 
const result = await Order.find({ amount: { $gt: 500 }, createdAt: { $gte: weekAgo } })
  .sort({ createdAt: -1 })
  .explain("executionStats");

console.log(result.executionStats.totalDocsExamined, result.executionStats.nReturned);

Comparing totalDocsExamined to nReturned tells you the "waste ratio" — if MongoDB examined 500,000 documents to return 40, that's a strong signal you're missing an index for this exact filter/sort shape.

❓ Follow-Up Questions

Q: Walk me through an explain() output — what do you look at first?

Answer: I look at the winning plan's stage first — IXSCAN vs COLLSCAN — then compare totalDocsExamined to nReturned to gauge how much wasted work happened.

Q: What's a covered query, and why is it fast?

Answer: A covered query is answered entirely from the index without touching the actual documents, because every field the query needs is present in the index itself.

Q: What's the difference between COLLSCAN and IXSCAN?

Answer: COLLSCAN scans every document in the collection sequentially; IXSCAN uses a B-tree index to jump directly to matching entries.

Q: You've indexed everything and it's still slow — what's next?

Answer: I'd check for in-memory sorts, large document sizes causing high I/O, lock contention, or whether the query is actually the bottleneck versus network/app-layer latency.

⚠️ Common Interview Traps
  • ❌ Adding an index always fixes a slow query.
    ✅ An index only helps if it matches the query's filter/sort shape — the wrong index, or wrong field order, gives no benefit at all.
📌 What to Remember
  • explain('executionStats') is the starting point for any optimization.
  • Compare totalDocsExamined vs nReturned to spot waste.
  • Covered queries never touch the raw documents.
  • skip() degrades badly at high offsets — prefer cursor pagination.
  • Index for your real, measured query patterns, not guesses.

What is schema design and how do you model relationships in MongoDB (1:1, 1:N, N:N)?

🎤 Interview Answer

Schema design in MongoDB is about deciding how to structure your documents to match how your application actually reads and writes data, rather than normalizing everything the way you would in SQL. For relationships, you choose between embedding — nesting related data directly inside a document — and referencing — storing an ID and looking the related data up separately, similar to a foreign key. For one-to-one relationships, like a user and their profile settings, I usually embed if the data is always accessed together. For one-to-many, it depends on the "many" side's size and growth: a blog post with a handful of comments can embed them, but a user with potentially unbounded orders should reference. For many-to-many, like students and courses, referencing with an array of IDs on one or both sides is usually cleanest, sometimes backed by a join collection for extra metadata on the relationship itself.

🧠 Understand It

MongoDB doesn't enforce relationships or joins the way relational databases do, so the schema design question becomes "what data do I read together, and how often does it change?" Embedding is fast for reads because everything comes back in one document, but it duplicates data and risks hitting MongoDB's 16MB document size limit if the embedded array grows unbounded. Referencing avoids duplication and unbounded growth but requires an extra query (or $lookup) to join data back together. The right choice is almost always driven by access patterns, not by what "feels normalized."

🔄 How It Works 
Ask: "Is this data read together most of the time?"
   ↓ yes                          ↓ no
Embed                          Reference
   ↓                              ↓
Watch document size          Use $lookup or populate()
💡 Practical Example

In a blog app, a post embeds a small array of tags (always read together, rarely grows large) but references its author by ID (the author document is large and shared across many posts).

💻 Code Example 
// Embedding: tags always travel with the post
const postSchema = new Schema({
  title: String,
  tags: [String],
  author: { type: Schema.Types.ObjectId, ref: "User" } // referenced
});

tags is a simple, bounded array so it's embedded directly for fast reads; author is referenced because user data is large, shared, and updated independently of any single post.

❓ Follow-Up Questions

Q: At what point do you switch from embedding to referencing?

Answer: When the embedded array can grow unbounded, when the embedded data changes independently of the parent, or when you need to query the embedded data on its own.

Q: How does the 16MB document limit constrain your design?

Answer: It's a hard ceiling — any embedded array that could realistically grow into the thousands (like activity logs) has to be referenced instead, or the document will eventually fail to save.

Q: How would you model a user with unbounded activity history?

Answer: Reference it — store activity events in their own collection with a userId field and an index on it, rather than embedding a growing array in the user document.

Q: How would you model a many-to-many that grows unbounded on both sides?

Answer: Use a separate join collection with the two IDs and any relationship-specific metadata, indexed on both foreign keys, instead of arrays on either side.

⚠️ Common Interview Traps
  • ❌ MongoDB schemas should be normalized like a SQL database by default.
    ✅ MongoDB favors denormalization driven by access patterns — embed what you read together, reference what grows or changes independently.
📌 What to Remember
  • Embed when data is read together and bounded in size.
  • Reference when data grows unbounded or is shared/updated independently.
  • 16MB document limit is a hard constraint on embedding.
  • Many-to-many often needs a join collection for relationship metadata.
  • Design schema around access patterns, not textbook normalization.

Explain data validation and how to enforce it in MongoDB.

🎤 Interview Answer

Data validation in MongoDB can happen at three levels: the application layer (like manual checks in your code), the ODM layer (Mongoose schemas with required fields, types, and custom validators), and the database layer itself using MongoDB's $jsonSchema validator attached directly to a collection. I typically rely on Mongoose for day-to-day validation because it's convenient and gives good error messages, but I also add a $jsonSchema validator at the collection level as a safety net, because Mongoose validation can be bypassed by anyone writing directly to the database, from a script, another service, or the mongo shell. The database-level validator is the one guarantee that bad data truly cannot get in, regardless of which code path writes it.

🧠 Understand It

Validation exists to prevent malformed or inconsistent data from corrupting your application's assumptions — a missing required field or wrong data type can cause bugs far downstream. MongoDB is schema-less by default, which is flexible but also means nothing stops you from saving garbage unless you explicitly add validation somewhere. The tradeoff is between validationLevel "strict" (validates all inserts and updates) and "moderate" (only validates already-valid documents on update, letting old non-conforming documents survive), which matters a lot when adding validation to a collection that already has messy data.

🔄 How It Works 
Write request
   ↓
App-layer checks (optional)
   ↓
Mongoose schema validation
   ↓
MongoDB $jsonSchema validator (final gate)
   ↓
Document persisted or rejected
💡 Practical Example

An e-commerce products collection enforces that price is a positive number and sku is a required string at the database level, so even a rogue admin script can't insert an invalid product.

💻 Code Example 
db.createCollection("products", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["sku", "price"],
      properties: {
        price: { bsonType: "number", minimum: 0 },
        sku: { bsonType: "string" }
      }
    }
  },
  validationLevel: "moderate"
});

This validator runs inside MongoDB itself, independent of any application code, so it's the last line of defense against invalid documents; "moderate" avoids breaking existing documents that don't yet conform.

❓ Follow-Up Questions

Q: Where should validation live — app layer, Mongoose, or $jsonSchema? Why?

Answer: Ideally all three: app layer for fast user feedback, Mongoose for developer convenience, and $jsonSchema as the non-bypassable final guarantee.

Q: What happens to existing documents when you add a validator?

Answer: By default existing documents aren't touched — validation only applies going forward — but with validationLevel 'strict', any future update to an old invalid document will fail until it's fixed.

Q: validationLevel: strict vs moderate — when would you use each?

Answer: Strict for new collections where you want zero tolerance; moderate when retrofitting validation onto a collection that already has non-conforming legacy documents.

Q: How do you introduce stricter validation on a collection with millions of dirty documents?

Answer: Start with moderate validation and validationAction 'warn' to log violations without rejecting writes, then run a backfill/migration to clean the data before tightening to strict.

⚠️ Common Interview Traps
  • ❌ Mongoose validation is enough on its own.
    ✅ Mongoose can be bypassed by any code that talks directly to MongoDB — a $jsonSchema validator is the only guarantee that holds regardless of the write path.
📌 What to Remember
  • Three layers: app code, Mongoose, $jsonSchema — use them together.
  • $jsonSchema is the only validation that can't be bypassed.
  • validationLevel strict validates everything; moderate spares old bad data.
  • validationAction 'warn' lets you audit before enforcing.
  • Validation prevents downstream bugs from malformed data.

What are transactions in MongoDB and when would you use them?

🎤 Interview Answer

Transactions in MongoDB let you group multiple operations, potentially across different collections or documents, so that they either all succeed together or all fail together — giving you ACID guarantees similar to a relational database. I reach for them when an operation genuinely needs atomicity across multiple documents, like transferring money between two accounts, where you need to debit one document and credit another as a single unit. That said, I try to design schemas to avoid needing multi-document transactions in the first place, because a single-document update is already atomic in MongoDB by default, and transactions carry a real performance cost — they require a replica set or sharded cluster, hold locks for their duration, and have limits on runtime and size.

🧠 Understand It

MongoDB guarantees atomicity on a single document automatically — if you update several fields in one document, that update either fully applies or doesn't happen at all. Transactions extend that same guarantee across multiple documents or collections, at the cost of coordination overhead. They exist for the cases where your data model genuinely can't be embedded into one document but still needs cross-document consistency. Overusing them is a sign the schema might benefit from redesign — many "I need a transaction" problems disappear if you embed the related data into a single document instead.

🔄 How It Works 
session.startTransaction()
   ↓
Operation 1 (e.g. debit account A)
   ↓
Operation 2 (e.g. credit account B)
   ↓
session.commitTransaction() — both applied atomically
   (on error → session.abortTransaction() — neither applied)
💡 Practical Example

A banking-style feature transferring funds between two user wallet documents needs a transaction so a crash between the debit and the credit can never leave money in limbo.

💻 Code Example 
const session = await mongoose.startSession();
session.startTransaction();
try {
  await Wallet.updateOne({ _id: fromId }, { $inc: { balance: -amount } }, { session });
  await Wallet.updateOne({ _id: toId }, { $inc: { balance: amount } }, { session });
  await session.commitTransaction();
} catch (err) {
  await session.abortTransaction();
  throw err;
} finally {
  session.endSession();
}

Both updates are tied to the same session; if either fails, abortTransaction rolls back the entire operation so the two wallets never end up out of sync.

❓ Follow-Up Questions

Q: What infrastructure do transactions require?

Answer: A replica set (even a single-node one for development) or a sharded cluster — transactions don't work on a standalone MongoDB instance.

Q: What's the performance cost of a multi-document transaction?

Answer: It holds locks across all involved documents for its duration and adds coordination overhead, which can hurt throughput under high concurrency.

Q: How do you handle retries on transient transaction errors?

Answer: MongoDB drivers expose a TransientTransactionError label; I wrap the transaction in a retry loop that catches that specific error and retries the whole transaction.

Q: How would you redesign a schema to avoid needing a transaction at all?

Answer: Embed the related data into a single document so the built-in single-document atomicity covers the use case without cross-document coordination.

⚠️ Common Interview Traps
  • ❌ Transactions work the same on any MongoDB deployment.
    ✅ They require a replica set or sharded cluster — a standalone instance can't run multi-document transactions.
📌 What to Remember
  • Single-document writes are already atomic in MongoDB — no transaction needed.
  • Transactions require a replica set or sharded cluster.
  • They add locking overhead and have runtime/size limits.
  • Prefer schema redesign (embedding) over reaching for transactions.
  • Always handle TransientTransactionError with a retry loop.

What is a capped collection?

🎤 Interview Answer

A capped collection has a fixed maximum size. When it reaches that limit, MongoDB reuses space by removing older documents. It preserves insertion order.

🧠 Simple Explanation / Remember
  • Useful for bounded logs
  • Recent activity
  • Temporary/rolling data
  • Not suitable when old records must be retained
💻 Example 
db.createCollection("logs", {
  capped: true,
  size: 100000
});
❓ Follow-up Question

Where can you use it? — Data where keeping only the most recent bounded history is acceptable.

⚠️ Interview / Machine-Coding Trap

Trap: Do not use a capped collection for permanent business history.

MongoDB

How does MongoDB handle concurrency?

🎤 Interview Answer

MongoDB's storage engine, WiredTiger, uses document-level concurrency control with optimistic techniques under the hood — multiple operations can read and write different documents simultaneously without blocking each other, and WiredTiger uses MVCC (multi-version concurrency control) so readers don't block writers and vice versa. For concurrent writes to the same document, MongoDB detects write conflicts and automatically retries the operation internally in most cases. For application-level concurrency concerns — like two requests both trying to decrement the same inventory count — I handle it with atomic update operators like $inc, or with a version field and a conditional update (optimistic locking) that only succeeds if the document hasn't changed since it was read.

🧠 Understand It

Concurrency control exists so that simultaneous operations don't corrupt data or produce inconsistent results. WiredTiger's document-level locking is much more granular than older collection-level locking, meaning unrelated documents almost never block each other. The remaining concern is when multiple operations target the very same document — that's where you need to think explicitly about atomic operators or optimistic locking patterns, because "read, modify in app code, write back" is inherently racy no matter how good the underlying engine is.

🔄 How It Works 
Two concurrent requests read same document
   ↓
Both try to update
   ↓
WiredTiger detects conflict on one
   ↓
MongoDB retries the conflicting operation automatically
   ↓
Or: app uses conditional update (optimistic lock) to reject stale writes explicitly
💡 Practical Example

An inventory system decrementing stock on checkout uses $inc with a condition (stock > 0) in the same atomic update, so two simultaneous purchases can never both succeed and oversell the last unit.

💻 Code Example 
const result = await Product.updateOne(
  { _id: productId, stock: { $gt: 0 } },
  { $inc: { stock: -1 } }
);
if (result.modifiedCount === 0) throw new Error("Out of stock");

The condition stock > 0 and the decrement happen as a single atomic operation, so even under heavy concurrent traffic, stock can never go negative.

❓ Follow-Up Questions

Q: What's WiredTiger's locking granularity?

Answer: Document-level, with MVCC snapshots so readers don't block writers — a big improvement over the old collection-level locking.

Q: How do you handle a lost update?

Answer: Use atomic operators like $inc/$set with conditions, or optimistic locking with a version field, instead of a read-modify-write pattern in application code.

Q: What's the difference between optimistic and pessimistic locking here?

Answer: Optimistic locking checks a version/condition at write time and rejects stale writes; pessimistic locking would explicitly lock the document first — MongoDB favors the optimistic approach.

Q: How would you implement a safe atomic counter under high contention?

Answer: Use $inc directly, which is atomic at the document level regardless of concurrent load, rather than reading the value, incrementing in code, and writing it back.

⚠️ Common Interview Traps
  • ❌ Reading a value, changing it in your code, then saving it back is safe in MongoDB.
    ✅ That read-modify-write pattern is racy under concurrency — use atomic operators like $inc or conditional updates instead.
📌 What to Remember
  • WiredTiger uses document-level locking with MVCC.
  • Readers don't block writers thanks to multi-version snapshots.
  • Use atomic operators ($inc, $set) instead of read-modify-write.
  • Optimistic locking with a version field guards against lost updates.
  • Conditional updates (e.g. stock > 0) prevent overselling races.

Explain change streams in MongoDB.

🎤 Interview Answer

Change streams let your application subscribe to real-time notifications of data changes — inserts, updates, deletes, replacements — happening on a collection, database, or entire deployment, without having to poll the database repeatedly. Under the hood they're built on the replication oplog, so they only work on a replica set or sharded cluster. I use change streams for things like triggering cache invalidation when a document updates, syncing data to a search index or another system in near real-time, or pushing live updates to connected clients over WebSockets. Each event includes a resume token, which is critical — if the connection drops, I persist that token and resume the stream from exactly where it left off instead of losing or duplicating events.

🧠 Understand It

Change streams exist because polling for changes ("check every 5 seconds if anything changed") wastes resources and adds latency. By tapping directly into the internal oplog, MongoDB can push changes to your application the moment they happen. The tricky part is reliability: your app can crash or disconnect, and you need a way to resume exactly where you left off rather than starting over — that's what resume tokens solve. Change streams still don't give you exactly-once guarantees for free; you have to design consumers to be idempotent.

🔄 How It Works 
Document changes
   ↓
Written to oplog
   ↓
Change stream reads oplog, filters to your subscription
   ↓
Event emitted { operationType, fullDocument, resumeToken }
   ↓
App processes event, persists resumeToken
💡 Practical Example

An inventory system uses a change stream on the products collection to invalidate a Redis cache entry the instant stock quantity changes, keeping the cache consistent without a polling job.

💻 Code Example 
const changeStream = db.collection("products").watch([], { fullDocument: "updateLookup" });
changeStream.on("change", async (event) => {
  await redis.del(`product:${event.documentKey._id}`);
  await saveResumeToken(event._id);
});

fullDocument: 'updateLookup' fetches the complete updated document (not just the diff) on update events, and saving the resume token after processing lets the app pick up exactly where it left off after a restart.

❓ Follow-Up Questions

Q: What happens if your app disconnects mid-stream? How do you resume?

Answer: You reopen the stream passing the last saved resumeToken, and MongoDB continues delivering events from exactly that point rather than from 'now'.

Q: What's a resume token and where do you persist it?

Answer: It's an opaque token identifying a position in the oplog; I persist it in a small collection or Redis key after each successfully processed event.

Q: What infrastructure do change streams require?

Answer: A replica set (minimum) or sharded cluster — they read from the oplog, which doesn't exist on a standalone instance.

Q: How do you guarantee exactly-once processing off a change stream?

Answer: You generally can't guarantee it natively — design consumers to be idempotent (e.g., upserts keyed by document ID) so at-least-once delivery behaves safely even with duplicates.

What's the difference between populate() and $lookup?

🎤 Interview Answer

populate() is a Mongoose-specific convenience feature that replaces a referenced ObjectId with the actual document it points to, but under the hood it does this by issuing a separate query to the referenced collection — essentially an application-level join done in two round trips. $lookup is MongoDB's native aggregation stage that performs the join inside the database itself, in a single query, and can use indexes on the foreign collection for the join condition. I use populate() for simple, low-volume cases where the convenience and readability of Mongoose syntax outweighs the extra round trip. I switch to $lookup inside an aggregation pipeline when I need to join and then further transform or filter the joined data, or when performance matters and I want to avoid the extra network round trip populate() implies.

🧠 Understand It

These solve the same underlying problem — combining data from two collections — but at different layers. populate() is convenient because it looks like a normal ORM feature, but it's really doing two queries under the hood, which matters at scale. $lookup does the join server-side as part of a single aggregation, which is more efficient for larger datasets or when combined with further pipeline stages like $group or $match on the joined fields.

💡 Practical Example

A simple blog admin page showing a post with its author's name might just use populate('author') for readability; a reporting pipeline joining orders with products to compute revenue by category would use $lookup inside aggregate().

💻 Code Example 
// populate() - two round trips, simple syntax
const post = await Post.findById(id).populate("author");

// $lookup - single round trip inside a pipeline
const result = await Order.aggregate([
  { $lookup: { from: "products", localField: "productId", foreignField: "_id", as: "product" } }
]);

populate() is readable for one-off document lookups; $lookup integrates the join directly into a larger pipeline, avoiding a second round trip and enabling further aggregation on the joined data.

❓ Follow-Up Questions

Q: populate() makes multiple round trips — when does that actually matter?

Answer: At high query volume or high latency to the database, where the extra round trip per request adds measurable overhead across thousands of requests.

Q: Can $lookup use an index on the foreign collection?

Answer: Yes — $lookup's join condition benefits from an index on the foreignField, just like a regular query would.

Q: What does populate() do that $lookup doesn't?

Answer: It integrates directly with Mongoose schemas and virtuals, giving you fully-typed model instances instead of raw joined documents.

Q: How would you avoid both in a read-heavy path?

Answer: Denormalize by embedding the frequently-needed fields (like author name) directly into the parent document, updated on write, avoiding a join at read time entirely.

⚠️ Common Interview Traps
  • ❌ populate() and $lookup are basically interchangeable.
    ✅ populate() is a Mongoose convenience doing two queries; $lookup is a native single-query aggregation join — they have real performance differences at scale.
📌 What to Remember
  • populate() = Mongoose convenience, two round trips.
  • $lookup = native aggregation join, single round trip.
  • $lookup benefits from indexes on the foreign collection.
  • Use $lookup when you need further pipeline processing.
  • Denormalizing avoids joins entirely in hot read paths.

How do you perform pagination in MongoDB efficiently?

🎤 Interview Answer

The naive approach uses skip() and limit(), but skip() gets progressively slower at high offsets because MongoDB still has to walk through and discard all the skipped documents before returning results — it doesn't jump straight to the offset. For real scalability I use cursor-based (keyset) pagination instead: I sort by a unique, indexed field like _id or createdAt, and instead of skipping N documents, I filter for documents "after" the last document's value from the previous page, using something like { _id: { $gt: lastSeenId } }. This lets MongoDB use the index to jump directly to the right position regardless of how deep into the results you are, so page 1000 is just as fast as page 1.

🧠 Understand It

skip() is intuitive but fundamentally doesn't scale — at offset 100,000, MongoDB examines and discards 100,000 documents every single time. Cursor-based pagination flips the approach: instead of saying "skip this many," you say "give me documents after this specific point," which an index can satisfy directly with a range scan. The tradeoff is you lose the ability to jump to an arbitrary page number directly (like "go to page 47") since you only know the cursor from the previous page — that's usually an acceptable tradeoff for infinite-scroll or "load more" UIs.

🔄 How It Works 
Page 1: find().sort({_id:1}).limit(20)
   ↓ remember last _id
Page 2: find({_id:{$gt:lastId}}).sort({_id:1}).limit(20)
   ↓ remember last _id
...continues in O(1) index lookups regardless of depth
💡 Practical Example

An infinite-scroll social feed uses cursor pagination on createdAt (with _id as a tiebreaker for equal timestamps) so scrolling deep into the feed never gets slower.

💻 Code Example 
const posts = await Post.find({ createdAt: { $lt: lastSeenCreatedAt } })
  .sort({ createdAt: -1 })
  .limit(20);

Using $lt against the last item's createdAt (with a compound index on createdAt) lets MongoDB jump directly to the right starting point via an index range scan, avoiding the cost of skip().

❓ Follow-Up Questions

Q: Why does skip() degrade at high offsets?

Answer: MongoDB has to scan and discard every skipped document before returning results — the cost grows linearly with the offset.

Q: Design cursor-based pagination — which field do you paginate on and why?

Answer: A unique, indexed, monotonically ordered field like _id or createdAt, so each cursor position is unambiguous and index-scannable.

Q: How do you paginate when the sort field isn't unique?

Answer: Add a tiebreaker field, typically _id, to the sort and cursor condition so equal timestamps don't cause skipped or duplicated results.

Q: How do you give a user a stable page while data is inserted underneath them?

Answer: Cursor pagination naturally handles this well since new inserts after your cursor position don't shift already-fetched results, unlike offset-based paging.

⚠️ Common Interview Traps
  • ❌ skip()/limit() is fine for pagination at any scale.
    ✅ skip() degrades badly at high offsets — cursor-based pagination is required for real scalability.
📌 What to Remember
  • skip() cost grows with offset — avoid for deep pagination.
  • Cursor pagination filters 'after last seen value' instead of skipping.
  • Always add a unique tiebreaker (like _id) to the sort.
  • Cursor pagination naturally handles concurrent inserts well.
  • You lose direct 'jump to page N' with cursor pagination — usually fine for feeds.

What is the use of the $facet stage?

🎤 Interview Answer

$facet lets you run multiple independent aggregation sub-pipelines against the same set of input documents in a single pass, and get all their results back together in one response. It's especially useful for building things like search results pages or dashboards where you need several different views of the same filtered data at once — for example, the paginated list of results, the total count, and category counts for filter sidebars, all computed from the same starting document set without querying the database three separate times.

🧠 Understand It

Without $facet, computing "results + total count + category breakdown" would mean either running three separate queries (with three separate round trips) or awkwardly combining everything into one pipeline output. $facet solves this by branching the pipeline: each named facet gets the same input documents and runs its own independent set of stages, and the final output groups all the facet results into one document. It saves round trips but has real cost — because it processes all facets against potentially large intermediate result sets, it can hit the 100MB memory limit if not paired with early filtering.

💡 Practical Example

A product search page runs one $facet with a "results" branch (sorted, paginated products) and a "categoryCounts" branch ($group by category), sourced from the same $match-filtered documents, in a single query.

💻 Code Example 
const [data] = await Product.aggregate([
  { $match: { category: "shoes", inStock: true } },
  { $facet: {
      results: [{ $sort: { price: 1 } }, { $skip: 0 }, { $limit: 20 }],
      totalCount: [{ $count: "count" }],
      categoryCounts: [{ $group: { _id: "$subCategory", count: { $sum: 1 } } }]
  }}
]);

All three branches — results, totalCount, categoryCounts — run against the same $match-filtered documents in one aggregation call, avoiding three separate database round trips.

❓ Follow-Up Questions

Q: What's the cost of $facet vs running separate queries?

Answer: $facet avoids extra round trips but processes the full input set for every facet branch in memory, so it can be more resource-intensive than well-indexed separate queries at scale.

Q: Can stages inside $facet use indexes?

Answer: Only the very first stage of the entire pipeline (before $facet) can use an index — stages inside each facet branch operate on already-in-memory documents.

Q: Give a real use case where $facet is the right tool.

Answer: A search results page needing results, total count, and filter facet counts all from the same filtered set in one round trip.

Q: How does $facet behave with respect to the memory limit?

Answer: Each facet branch is still subject to the 100MB limit individually, so heavy branches may need allowDiskUse or should filter more aggressively before $facet.

⚠️ Common Interview Traps
  • ❌ $facet is just a way to run multiple queries in parallel.
    ✅ It runs multiple sub-pipelines against the same already-filtered input in a single pass, not independent parallel queries against the collection.
📌 What to Remember
  • $facet runs multiple sub-pipelines on the same input documents.
  • Great for combining results + count + category breakdowns in one call.
  • Only the pipeline stage before $facet can use an index.
  • Each facet branch still respects the 100MB memory limit.
  • Filter aggressively with $match before $facet to control cost.

How does MongoDB handle horizontal scaling?

🎤 Interview Answer

MongoDB scales horizontally through sharding, where a large collection is split across multiple servers (shards) based on a shard key you choose. Each shard holds a portion of the data, and a routing layer called mongos directs queries to the right shard or shards based on that key, so the cluster as a whole can handle far more data and throughput than a single server could. The critical decision is choosing a good shard key — one with high cardinality and an even write distribution — because a bad shard key creates "hot shards" where most traffic hits one server, defeating the purpose of sharding entirely. I'd only reach for sharding once vertical scaling, indexing, and read replicas have genuinely been exhausted, since it adds significant operational complexity.

🧠 Understand It

A single MongoDB server has finite CPU, memory, and disk throughput; sharding lets you scale beyond that ceiling by distributing data and load across many machines. The shard key determines how documents are distributed — ranged sharding keeps similar key values together (good for range queries, but risks hotspots), while hashed sharding distributes evenly (better write distribution, but breaks range query efficiency). Sharding is powerful but not free: it complicates queries that don't include the shard key, transactions, and operational tasks like backups.

🔄 How It Works 
Client query
   ↓
mongos router (reads shard key from query)
   ↓
Routes to relevant shard(s) based on chunk ranges
   ↓
Each shard is itself a replica set (for HA)
   ↓
Results merged and returned
💡 Practical Example

A multi-tenant SaaS platform shards its main data collection on tenantId (hashed), so each tenant's data and load is spread evenly and no single large tenant can overwhelm one shard.

💻 Code Example 
sh.enableSharding("saasApp");
sh.shardCollection("saasApp.events", { tenantId: "hashed" });

Hashed sharding on tenantId distributes tenants evenly across shards, avoiding hotspots that a naturally skewed field (like a sequential ID) could cause.

❓ Follow-Up Questions

Q: How do you choose a shard key? What makes a bad one?

Answer: High cardinality, even distribution of writes, and alignment with your most common query patterns; a bad key is low-cardinality or monotonically increasing, which creates hot shards.

Q: What's the difference between ranged and hashed sharding?

Answer: Ranged keeps similar values together for efficient range queries but risks hotspots; hashed distributes evenly for write balance but makes range queries scatter-gather.

Q: What's a jumbo chunk and how do you avoid it?

Answer: A chunk that's grown too large to split, usually from a low-cardinality shard key; avoided by choosing a shard key with enough distinct values to split evenly.

Q: Can you change a shard key after the fact? What's the process?

Answer: As of newer MongoDB versions you can reshard a collection, but it's a heavyweight background operation — historically it required migrating to a new collection.

⚠️ Common Interview Traps
  • ❌ Sharding automatically makes everything faster.
    ✅ A poorly chosen shard key can make things worse by creating a hot shard — sharding is not a substitute for good indexing and query design.
📌 What to Remember
  • Sharding distributes data across servers via a chosen shard key.
  • mongos routes queries; each shard is typically its own replica set.
  • High-cardinality, evenly-distributed shard keys avoid hot shards.
  • Ranged sharding favors range queries; hashed favors write distribution.
  • Exhaust indexing/vertical scaling before reaching for sharding.

Difference between embedded documents vs. referenced documents.

🎤 Interview Answer

Embedded documents nest related data directly inside a parent document, so reading the parent gives you everything in one query — like storing a shipping address object directly inside an order document. Referenced documents instead store just an ID pointing to a document in another collection, requiring a separate query or a $lookup/populate() to retrieve the related data — similar to a foreign key in a relational database. I embed when the data is always accessed together, doesn't grow unbounded, and belongs conceptually to the parent, like an address on an order. I reference when the related data is large, shared across many parents, updated independently, or could grow without limit, like a user's full order history.

🧠 Understand It

This choice is the core tradeoff of MongoDB schema design. Embedding optimizes for read performance (one document, one query) at the cost of potential duplication and document size growth. Referencing optimizes for update flexibility and avoids duplication, at the cost of an extra lookup on read. Neither is universally "correct" — the decision should follow how your application actually reads and writes that data.

💡 Practical Example

An order document embeds the shipping address (read together, doesn't change independently) but references the customer by ID (customer data is large, shared across many orders, and updated separately).

💻 Code Example 
const orderSchema = new Schema({
  customer: { type: Schema.Types.ObjectId, ref: "Customer" }, // referenced
  shippingAddress: { street: String, city: String, zip: String } // embedded
});

shippingAddress is embedded because it's a snapshot specific to this order and always read with it; customer is referenced because customer data is large and shared across potentially thousands of orders.

❓ Follow-Up Questions

Q: How does update frequency influence the choice?

Answer: Data that changes frequently and independently of the parent is better referenced, so updates don't require touching every parent document that embeds it.

Q: Explain the read vs write amplification tradeoff.

Answer: Embedding reduces read amplification (one document, one read) but can increase write amplification if duplicated data needs updating in many places; referencing does the opposite.

Q: Give an example where embedding is clearly the wrong call.

Answer: Embedding a user's entire unbounded order history directly on the user document — it would grow indefinitely and risk hitting the 16MB document limit.

Q: How do you handle a document that grows past a reasonable size after launch?

Answer: Migrate the growing embedded array out into its own referenced collection, backfilling existing data and updating the application to query it separately.

⚠️ Common Interview Traps
  • ❌ Always embed for performance since MongoDB is document-based.
    ✅ Embedding unbounded or frequently-changing data causes real problems — the right choice depends on access patterns, not a blanket rule.
📌 What to Remember
  • Embed: read together, bounded size, belongs to the parent.
  • Reference: shared, independently updated, or unbounded growth.
  • Embedding optimizes reads; referencing optimizes update flexibility.
  • 16MB document limit caps how much you can safely embed.
  • Migrate embedded data to referenced if it starts growing unbounded.

How do you back up and restore a MongoDB database?

🎤 Interview Answer

There are a few approaches depending on scale and requirements. mongodump/mongorestore does a logical backup — it exports documents as BSON and can restore them into any MongoDB version, which is flexible but slower for large datasets. Filesystem snapshots capture the underlying data files at the storage layer, which is much faster for large deployments but requires careful coordination to ensure consistency. For production systems on Atlas, I'd rely on Atlas's continuous backup, which does point-in-time recovery based on the oplog, letting you restore to any specific second rather than just the last full backup. My general rule is: use mongodump for smaller datasets or migrating data between environments, and use continuous/snapshot-based backups with point-in-time recovery for anything running in production at real scale.

🧠 Understand It

Backups exist because hardware fails, humans make mistakes, and bad deploys happen — you need a way to recover data that isn't dependent on the same system that might have caused the data loss. Logical backups (mongodump) are portable and human-inspectable but slow to restore at scale, since they replay every document. Physical/snapshot backups are fast to restore because they're just the underlying storage files, but they're tied to compatible MongoDB versions and storage engines. Point-in-time recovery, layered on top of snapshots via the oplog, is what actually lets you undo "we deleted the wrong data five minutes ago" instead of just "restore to last night's backup."

💡 Practical Example

A production e-commerce database uses Atlas's continuous backup so that if a deployment bug corrupts order data at 2:15pm, the team can restore to 2:14pm precisely instead of losing a full day of orders by restoring from last night's snapshot.

💻 Code Example 
// Logical backup and restore
mongodump --uri="mongodb://localhost:27017/shopDb" --out=./backup
mongorestore --uri="mongodb://localhost:27017/shopDb" ./backup/shopDb

mongodump exports every document to BSON files; mongorestore replays them into a target database — portable across environments but not the fastest option for very large datasets.

❓ Follow-Up Questions

Q: mongodump vs filesystem snapshot vs Atlas continuous backup — when each?

Answer: mongodump for small datasets or environment migration; filesystem snapshots for fast full-cluster backups; Atlas continuous backup for production point-in-time recovery.

Q: What's the difference between a logical and a physical backup?

Answer: Logical backups export data in a portable document format (slow, flexible); physical backups copy the raw storage files (fast, version/engine-dependent).

Q: How do you restore a single collection without touching the rest?

Answer: mongorestore supports targeting a specific database and collection path from the dump directory, restoring only that collection.

Q: What's your RPO/RTO target, and how does it change your strategy?

Answer: A low RPO (minimal data loss) pushes toward continuous oplog-based backup; a low RTO (fast recovery) favors snapshot restores over slow logical restores.

⚠️ Common Interview Traps
  • ❌ Having a nightly backup means you're protected from data loss.
    ✅ A nightly backup only protects against losing up to a full day of data — point-in-time recovery is needed for tighter recovery objectives.
📌 What to Remember
  • mongodump/mongorestore = logical, portable, slower at scale.
  • Filesystem snapshots = fast, tied to storage engine/version.
  • Atlas continuous backup enables point-in-time recovery via the oplog.
  • RPO/RTO targets should drive your backup strategy choice.
  • Always actually test a restore — an untested backup is a guess.

How can you enforce uniqueness on a field?

🎤 Interview Answer

You create a unique index on the field, which tells MongoDB to reject any insert or update that would create a duplicate value for that field across the collection. For example, creating a unique index on email in a users collection guarantees at the database level that no two users can ever share the same email, regardless of which code path performs the insert. If you need uniqueness only among a subset of documents — like unique usernames only among active accounts — you'd combine it with a partial index so deleted or inactive documents don't count toward the uniqueness constraint.

🧠 Understand It

Application-level checks like "query for an existing email before inserting" are vulnerable to race conditions — two simultaneous signups could both pass the check before either insert completes. A unique index enforces the constraint atomically at the database level, so even under concurrent writes, only one document can ever hold a given value. This is the same category of guarantee a UNIQUE constraint gives you in a relational database.

💡 Practical Example

A signup flow relies on a unique index on the email field so that even if two requests race to register the same email simultaneously, only one succeeds and the other gets a duplicate-key error to handle gracefully.

💻 Code Example 
db.users.createIndex({ email: 1 }, { unique: true });

// Handling the resulting error
try {
  await User.create({ email });
} catch (err) {
  if (err.code === 11000) throw new Error("Email already registered");
}

The unique index guarantees atomicity at the database layer; error code 11000 is MongoDB's duplicate-key error, which the app catches to return a clean, user-friendly message.

❓ Follow-Up Questions

Q: How does a unique index behave with null or missing fields?

Answer: By default, MongoDB treats missing/null values as equal, so you can only have one document with a missing or null value unless the index is also sparse.

Q: How do you enforce uniqueness on only a subset of documents?

Answer: Use a partial index with a filter expression, e.g. only enforcing uniqueness where { status: 'active' }.

Q: What happens if you build a unique index on data that already has duplicates?

Answer: The index creation fails with an error listing the duplicate keys — you have to clean up the duplicates first.

Q: Can you enforce uniqueness across a sharded cluster on a non-shard-key field?

Answer: Only if the unique field is a prefix of the shard key or the shard key itself — otherwise uniqueness can't be guaranteed cluster-wide since shards can't coordinate on non-shard-key uniqueness.

⚠️ Common Interview Traps
  • ❌ Checking for an existing value in application code before inserting is enough.
    ✅ That approach has a race condition under concurrent requests — a unique index is the only way to guarantee it atomically.
📌 What to Remember
  • A unique index enforces the constraint atomically at the database layer.
  • Application-level pre-checks are vulnerable to race conditions.
  • Duplicate-key errors have code 11000 — catch and handle them.
  • Sparse/partial indexes control how null/missing values are treated.
  • Cluster-wide uniqueness requires the field to be part of the shard key.

Explain middleware and the types of middleware in Express.

🎤 Interview Answer

Middleware is a function that runs during the request-response lifecycle. It can read/modify req and res, end the response, or call next() to continue.

🧠 Simple Explanation / Remember
  • Application-level middleware
  • Router-level middleware
  • Built-in middleware such as express.json()
  • Third-party middleware such as cors()
  • Error-handling middleware
💻 Example 
app.use(express.json());

app.use((req, res, next) => {
  console.log(req.method, req.url);
  next();
});
❓ Follow-up Question

What happens if middleware neither sends a response nor calls next()? — The request can hang because the chain does not continue.

⚠️ Interview / Machine-Coding Trap

Trap: Error middleware has four parameters: (err, req, res, next).

🎤 Interview Answer

A request enters the Express application, passes through matching middleware and route handlers, and eventually sends a response or reaches the error handler.

🧠 Simple Explanation / Remember
  • Client → middleware → router → controller → response
  • Middleware can authenticate, validate, log, parse, or transform
  • Order matters
💻 Example

❓ Follow-up Question

⚠️ Interview / Machine-Coding Trap

Trap: Registering auth middleware after a route does not protect that earlier route.

Express.js

What is the use of next() in Express?

🎤 Interview Answer

next() passes control to the next matching middleware or route handler. next(err) passes control to error-handling middleware.

🧠 Simple Explanation / Remember
  • next() → continue
  • next(err) → error flow
  • Without next() or a response, the request may remain pending
💻 Example 
app.use((req, res, next) => {
  req.requestTime = Date.now();
  next();
});
❓ Follow-up Question

Can next() send a response? — No. It transfers control; a middleware must send the response itself if it is ending the request.

⚠️ Interview / Machine-Coding Trap

Trap: Do not call next() after sending a response unless you deliberately understand the consequences.

Difference between synchronous and asynchronous middleware.

🎤 Interview Answer

Synchronous middleware completes its work before returning. Asynchronous middleware performs work that may involve promises, I/O, or callbacks and must correctly handle completion/errors.

🧠 Simple Explanation / Remember
  • Sync example → simple validation
  • Async example → database lookup
  • Async errors should be forwarded to the error handler
  • Modern Express versions support rejected promises in route/middleware flows; still use a clear error strategy
💻 Example 
app.use(async (req, res, next) => {
  try {
    req.user = await findUser(req.headers.authorization);
    next();
  } catch (err) {
    next(err);
  }
});
❓ Follow-up Question

Why does async middleware need special care? — Errors from asynchronous work must reach the centralized error handler rather than becoming unhandled failures.

⚠️ Interview / Machine-Coding Trap

Trap: Do not leave a rejected promise unhandled or forget to end/continue the request.

React.js

What are custom hooks and when would you use them?

🎤 Interview Answer

A custom hook is a JavaScript function whose name starts with use and that composes React hooks to reuse stateful logic across components.

🧠 Simple Explanation / Remember
  • Reuse behavior, not UI markup
  • Examples: useFetch, useDebounce, useAuth
  • Custom hooks can call other hooks
💻 Example 
function useOnlineStatus() {
  const [online, setOnline] = useState(navigator.onLine);

  useEffect(() => {
    const update = () => setOnline(navigator.onLine);
    window.addEventListener("online", update);
    window.addEventListener("offline", update);
    return () => {
      window.removeEventListener("online", update);
      window.removeEventListener("offline", update);
    };
  }, []);

  return online;
}
❓ Follow-up Question

Why not copy-paste the logic? — A custom hook centralizes behavior and makes it reusable and testable.

⚠️ Interview / Machine-Coding Trap

Trap: Custom hooks share logic, not the same state instance; each component calling the hook gets its own hook state.

MongoDB

What is Atlas Vector Search and when would you use it?

🎤 Interview Answer

Atlas Vector Search is MongoDB's built-in capability for storing high-dimensional vector embeddings alongside your normal document data and running approximate nearest-neighbor search on them — which is the core operation behind semantic search and retrieval-augmented generation. Instead of matching on exact keywords, it finds documents whose embeddings are mathematically closest to a query embedding, so a search for "affordable running shoes" can match a product described as "budget-friendly jogging sneakers" even though no words overlap. I'd use it whenever I'm building an AI feature that needs semantic similarity — a RAG chatbot pulling relevant document chunks, a recommendation engine, or "find similar items" — and I want to keep that data in the same database as the rest of my application instead of standing up a separate dedicated vector database.

🧠 Understand It

Traditional text indexes match on exact words or stems; vector search instead compares meaning. An embedding model converts text (or images) into a fixed-length array of numbers that captures semantic meaning, and similar concepts end up close together in that vector space. Atlas Vector Search builds a specialized index (using an algorithm like HNSW) over those vectors so it can find the nearest neighbors quickly even across millions of documents, without having to compare the query against every single vector. You use it when keyword matching is too rigid for what users actually mean; you skip it for simple exact-match or structured queries, where a normal index is faster and simpler.

🔄 How It Works 
Text/content
   ↓
Embedding model → vector (e.g. 1536 floats)
   ↓
Store vector in document, build Atlas Vector Search index
   ↓
Query text → embed → $vectorSearch finds nearest vectors
   ↓
Return most semantically similar documents
💡 Practical Example

A support-ticket search tool embeds every past resolved ticket; when an agent describes a new issue, vector search surfaces the most semantically similar past tickets even if the wording is completely different.

💻 Code Example 
const results = await db.collection("tickets").aggregate([
  {
    $vectorSearch: {
      index: "ticket_vector_index",
      path: "embedding",
      queryVector: queryEmbedding,
      numCandidates: 150,
      limit: 5
    }
  }
]).toArray();

queryVector is the embedding of the new issue's text; numCandidates controls how many approximate candidates are considered before narrowing to the top limit results, trading a bit of speed for recall.

❓ Follow-Up Questions

Q: How do you choose the number of dimensions and the similarity metric?

Answer: Dimensions are dictated by your embedding model (e.g. 1536 for OpenAI's text-embedding-3-small); similarity metric is usually cosine for normalized text embeddings, or dot product/euclidean for others.

Q: What's the difference between ANN and exact nearest-neighbour search?

Answer: Exact search compares the query against every vector for guaranteed correctness but doesn't scale; ANN (approximate nearest neighbor) uses index structures like HNSW to find very-likely-correct neighbors much faster.

Q: How does vector search differ from a normal text index?

Answer: A text index matches on tokens/stems; vector search matches on semantic similarity in embedding space, so it can find conceptually related results with no shared words.

Q: How do you keep the vector index in sync when source documents change?

Answer: Re-embed and update the vector field whenever the source text changes, typically via a change stream or an application-level hook, since Atlas doesn't auto-regenerate embeddings for you.

  • ❌ Vector search replaces the need for regular indexes and filters.
    ✅ Vector search is for semantic similarity specifically — you still combine it with metadata filters and regular indexes for structured constraints.
📌 What to Remember
  • Vector search finds semantic similarity, not exact keyword matches.
  • Requires storing an embedding vector alongside your document.
  • Uses ANN algorithms like HNSW for scalable nearest-neighbor lookup.
  • numCandidates trades speed for recall accuracy.
  • Re-embedding is your responsibility whenever source content changes.

What is the difference between $vectorSearch and traditional $match?

🎤 Interview Answer

$match filters documents based on exact criteria — equality, ranges, regex — it's boolean, a document either satisfies the condition or it doesn't. $vectorSearch instead ranks documents by similarity to a query vector, returning the closest matches even if none of them are a perfect match; it's inherently a "best effort, ranked" operation rather than a strict filter. In practice I combine both: $vectorSearch has a built-in filter option (or you can follow it with $match) so you narrow the semantic search to only documents matching certain metadata, like tenant or category, before or while ranking by similarity. $vectorSearch also has to be the first stage in a pipeline, unlike $match which can appear anywhere.

🧠 Understand It

These two solve fundamentally different problems: $match answers "does this document meet my exact criteria?" while $vectorSearch answers "how semantically close is this document to what I mean?" Treating vector search as a drop-in replacement for $match is a mistake — you lose exact filtering capability. The real power comes from combining them: use metadata filters to scope the candidate set (like "only this tenant's documents") and vector search to rank by relevance within that scope.

💡 Practical Example

A multi-tenant SaaS search feature filters to the current tenant's documents while ranking by semantic similarity to the user's query, so cross-tenant data leakage is impossible regardless of embedding similarity.

💻 Code Example

  {
    $vectorSearch: {
      index: "chunks_index",
      path: "embedding",
      queryVector: queryEmbedding,
      filter: { tenantId: currentTenantId },

  }

The filter option scopes candidates to the current tenant before ranking, combining exact-match safety with semantic ranking in a single index-backed stage.

Answer: Start with numCandidates around 10-20x the limit, then measure — raise it if relevant results are being missed, lower it if latency is too high for acceptable recall.
